# 코드 작업 수행 pilot

## 결과

일반 검색과 kfind 조건 모두 4개 과제를 수정하고 원본 검증을 통과했다. 검색과 파일 열람은
각각 4회로 같다. 이 입력에서는 작업 완료율이나 호출 횟수의 개선을 확인하지 못했다.
kfind의 후보 줄과 JSON 출력량은 적었지만 실제로 열어 본 source 파일은 같았다.

| 검색 조건 | 완료 과제 | 검색 / 파일 열람 | 수정 작업 | 후보 파일 합 | 후보 줄 합 | 검색 stdout bytes | 파일 열람 bytes |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| rg 어간·활용형 검색 | 4 / 4 | 4 / 4 | 4 | 7 | 15 | 8,311 | 6,019 |
| kfind Agent 검색 | 4 / 4 | 4 / 4 | 4 | 6 | 11 | 5,875 | 6,019 |

검색 stdout은 각 CLI의 JSON 전체이며 포맷이 다르다. Byte 감소를 모델 token·비용 감소로
환산하지 않는다. 같은 파일이 다른 과제에서 검색되면 별도로 센다. 모든 과제는 검색 1회와
파일 열람 1회로 대상 코드를 고른 뒤 수정했다. 두 조건의 과제별 최종 patch는 같다.

## 과제와 검증

| 과제 | 요구사항 | 수정 전 | 수정 후 | 수행 순서 |
| --- | --- | --- | --- | --- |
| 문자열 처리 | 양쪽 공백 제거, 문자열 덧붙이기, 치환 | 컴파일 실패 | 원본 테스트 3개 통과 | rg → kfind |
| 과일 바구니 | 없는 종류만 추가하고 기존 수량 보존 | 원본 테스트 3개 실패 | 원본 테스트 4개 통과 | kfind → rg |
| 양의 정수 생성 | 음수·0의 오류 구분 | 원본 테스트 1개 실패 | 원본 테스트 1개 통과 | rg → kfind |
| 스레드 결과 수집 | 모든 스레드를 기다리고 반환값 수집 | 컴파일 실패 | 원본 main 검증 및 10개 완료·반환값 확인 | kfind → rg |

과제·검증 명령·수행 순서를 먼저 고정했다. 조건마다 같은 9개 파일을 복사해 사용하고
수정 전 실패부터 확인했다. 원본 테스트와 main의 완료 검증은 수정하지 않았다.
Rust 코드의 실제 컴파일·실행 결과를 기록했으며, 검색 성공만으로 작업 완료를 판정하지 않았다.

## 파일 관련성

각 과제가 수정해야 하는 파일 1개를 양성, 나머지 8개를 음성으로 정했다. 아래 값은
검색된 **파일의 과제 관련성**이며 형태 분석 정확도가 아니다. 모든 파일에 정답이 있어
누락·다른 파일 반환을 함께 센다. Contract review는 0건이며 raw와 adjusted는 같다.

| 조건 | raw TP / FP / TN / FN | raw P / R / F1 (%) | adjusted TP / FP / TN / FN | adjusted P / R / F1 (%) |
| --- | --- | --- | --- | --- |
| rg | 4 / 3 / 29 / 0 | 57.14 / 100 / 72.73 | 4 / 3 / 29 / 0 | 57.14 / 100 / 72.73 |
| kfind | 4 / 2 / 30 / 0 | 66.67 / 100 / 80.00 | 4 / 2 / 30 / 0 | 66.67 / 100 / 80.00 |

## 조건과 한계

- 측정일: 2026-09-12. kfind 코드: `209427e27229ef7d95e6a52e70c62fd21626e0a5`.
- 입력은 기존 source manifest의 Rustlings 한국어 6개 파일과 Kubernetes 한국어 문서 3개 파일이다.
  Revision·license·SHA-256과 실제 읽은 내용은 원본 JSON에 보존한다.
- rg에는 완성된 표제어만 주지 않고 `공백`, `붙여`, `바꿔`, `추가`, `반환`, `기다`를 사용했다.
  kfind에는 대응하는 동사 표제어를 사용했다. 두 조건 모두 후속 검색을 허용했지만 필요하지 않았다.
- kfind는 embedded/any, 명시적 동사 POS와 빈 사용자 사전을 사용했다. 두 조건 모두 JSON을 읽었다.
- 같은 Codex 에이전트가 수행한 비맹검 pilot이다. 수행 전 4개 source 파일을 읽었고,
  기존 검색 평가에서도 이 입력을 사용했다. 후행 조건에는 선행 해법의 학습 효과가 있다.
  8회를 독립적인 모델 표본으로 세거나 일반적인 에이전트 성공률 차이를 추정하지 않는다.
- 작은 교육용 단일 파일 과제이며 미지의 실제 프로젝트 결함을 대표하지 않는다.
  파일명·주석과 요구사항의 대응도 명확하므로 검색 차이를 드러내기 쉬운 과제만 고르지 않았다.
- 모델 판단·수정 도구 시간과 호출 간 대기는 계측하지 않았다. JSON의 `elapsed_ms`는 해당
  subprocess 실행만 측정한다. 검색 시간 합은 rg 43.425 ms, kfind 44.279 ms였으나
  단회 실행·OS cache·프로세스 시작 비용이 포함되어 속도 우열이나 회귀 판정에 쓰지 않는다.

## 재현

원본 JSON은 과제, 수행 순서, 모든 검색·열람·검증 argv와 stdout/stderr, 수정 patch,
source와 binary checksum을 포함한다. 원본 source는
[Rustlings 한국어](https://github.com/eoncheole/rustlings-kr/tree/5afb3e613b306d0803d8f2f6ab6d1c3e26c12c35)
(기여자, MIT)와
[Kubernetes 문서](https://github.com/kubernetes/website/tree/11ed97b8bc76e86d4b5ed330ad27df67ec2b2b8b)
(기여자, CC BY 4.0)다. 수정본은 평가용 임시 복사본이며 원본 프로젝트에 반영하지 않는다.

```sh
python3 tools/morph-compare/real_corpus/replay_code_tasks.py \
  docs/benchmarks/2026-09-12-code-task-pilot.json \
  --source-cache target/task-search/sources \
  --work-root target/code-task-replay
```

이 명령은 source checksum, 수정 전 실패, patch 적용, 원본 검증 보존과 수정 후 성공을
재확인한다. 에이전트의 검색·수정 판단을 다시 수행하는 명령은 아니며 새로운 trial로 세지 않는다.
검색 자체는 JSON의 `search` argv에서 binary·resource 경로를 현재 환경으로 바꿔 재현한다.
